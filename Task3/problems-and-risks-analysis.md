# Задание 3: Анализ проблем и рисков текущей архитектуры

## Текущая архитектура взаимодействия

### Схема взаимодействий (AS-IS):

1. **ins-product-aggregator → Страховые компании**
   - Синхронный REST API вызов к 5 страховым компаниям
   - Агрегация данных в единый список
   - Возврат результата в рамках того же запроса

2. **core-app → ins-product-aggregator**
   - Периодический опрос каждые 15 минут (REST API)
   - Локальное кэширование данных о продуктах и тарифах
   - Синхронный запрос

3. **ins-comp-settlement → ins-product-aggregator**
   - Ночной запрос раз в сутки (REST API)
   - Локальное кэширование данных
   - Синхронный запрос

4. **ins-comp-settlement → core-app**
   - Ежедневный запрос для получения оформленных страховок (REST API)
   - Синхронный запрос

---

## Выявленные проблемы и риски

### Проблема 1: Неэффективность периодического опроса (Polling)

**Описание:**
- core-app опрашивает ins-product-aggregator каждые 15 минут независимо от наличия изменений
- ins-comp-settlement делает запрос раз в сутки

**Риски при масштабировании:**
- При росте с 5 до 10 страховых компаний время обработки запроса увеличится в 2 раза
- Неиспользуемые запросы расходуют ресурсы:
  - Если данные не изменились, запрос выполняется впустую
  - При 96 запросах в день (каждые 15 мин) × 10 компаний = 960 внешних вызовов
- Задержка обновления данных до 15 минут (пользователи видят устаревшую информацию)
- Высокая нагрузка на ins-product-aggregator даже при отсутствии изменений

**Влияние на бизнес:**
- Увеличение затрат на инфраструктуру (избыточные вычисления)
- Риск показа устаревших данных клиентам
- Снижение конкурентоспособности (конкуренты могут обновлять данные быстрее)

**Оценка критичности:** 🔴 Высокая

---

### Проблема 2: Синхронные вызовы создают узкое горлышко

**Описание:**
- ins-product-aggregator синхронно опрашивает все страховые компании
- Время ответа = сумма времен всех страховых компаний + время агрегации
- При текущих 5 компаниях: если каждая отвечает 2 секунды, общее время = 10+ секунд

**Риски при масштабировании:**
- При 10 компаниях время ответа может достичь 20+ секунд
- Если одна страховая компания "медленная" (5-10 сек), блокируется весь запрос
- Timeout'ы будут происходить чаще
- Каскадные отказы: задержка в одном сервисе влияет на все зависимые сервисы

**Сценарий отказа:**
1. Страховая компания #3 начинает отвечать за 30 секунд
2. Все запросы к ins-product-aggregator висят 30+ секунд
3. core-app получает timeout
4. Пользователи видят ошибки или устаревшие данные

**Влияние на бизнес:**
- Ухудшение пользовательского опыта (долгая загрузка)
- Снижение конверсии (пользователи уходят при долгой загрузке)
- Увеличение нагрузки на поддержку (жалобы клиентов)

**Оценка критичности:** 🔴 Критическая

---

### Проблема 3: Отсутствие изоляции отказов

**Описание:**
- Отказ или задержка одной страховой компании блокирует получение данных от всех остальных
- Нет механизма partial response (частичного ответа)

**Риски при масштабировании:**
- Вероятность отказа хотя бы одного из 10 партнеров значительно выше, чем из 5
- Формула: P(отказ хотя бы 1 из N) = 1 - (1 - P(отказ_1))^N
- Если P(отказ_1) = 5%, то:
  - Для 5 компаний: P = 1 - 0.95^5 = 22.6%
  - Для 10 компаний: P = 1 - 0.95^10 = 40.1%
- Почти вдвое выше шанс полного отказа системы!

**Сценарий:**
1. Одна из 10 страховых компаний недоступна
2. ins-product-aggregator не может вернуть результат (timeout)
3. core-app не обновляет данные
4. Пользователи не видят предложения от 9 работающих компаний

**Влияние на бизнес:**
- Потеря выручки (клиенты не могут оформить страховку)
- Нарушение SLA с партнерами
- Репутационные риски

**Оценка критичности:** 🔴 Критическая

---

### Проблема 4: Дублирование данных и их рассинхронизация

**Описание:**
- core-app и ins-comp-settlement хранят локальные копии данных о продуктах
- Каждый сервис обновляет данные в своем расписании:
  - core-app: каждые 15 минут
  - ins-comp-settlement: раз в сутки
- Нет единого источника правды (Single Source of Truth)

**Риски при масштабировании:**
- Разные сервисы показывают разные данные в один момент времени
- ins-comp-settlement может работать с данными, устаревшими на 24 часа
- При добавлении новых сервисов проблема усугубится
- Сложность синхронизации растет экспоненциально с количеством сервисов

**Сценарий:**
1. Страховая компания изменяет тариф в 10:00
2. core-app обновит данные в 10:15 (следующий опрос)
3. ins-comp-settlement обновит данные только на следующий день в 02:00
4. Расчеты агентских премий выполняются по устаревшим тарифам
5. Финансовые расхождения со страховыми компаниями

**Влияние на бизнес:**
- Финансовые убытки из-за неверных расчетов
- Юридические риски (неверные условия договоров)
- Потеря доверия партнеров

**Оценка критичности:** 🟡 Средняя (но растет с масштабом)

---

### Проблема 5: Тесная связность (Tight Coupling) между сервисами

**Описание:**
- ins-comp-settlement напрямую зависит от core-app для получения данных о страховках
- Синхронный REST API создает прямую зависимость
- Если core-app недоступен, ins-comp-settlement не может выполнить свою функцию

**Риски при масштабировании:**
- При добавлении новых типов страховок (не только жизнь, но и ОСАГО, недвижимость):
  - Потребуется изменять API между сервисами
  - Версионирование API станет проблемой
  - Обратная совместимость усложнится
- Каждое изменение в core-app может сломать ins-comp-settlement
- Сложно делать независимые релизы сервисов

**Сценарий:**
1. core-app обновляется (добавлено новое поле в API)
2. ins-comp-settlement начинает получать ошибки (несовместимость версий)
3. Ночная задача формирования реестра падает
4. Страховые компании не получают данные для расчета премий
5. Задержка выплат InsureTech

**Влияние на бизнес:**
- Замедление разработки (координация изменений между командами)
- Увеличение времени вывода новых продуктов на рынок
- Риск каскадных отказов

**Оценка критичности:** 🟡 Средняя

---

### Проблема 6: Отсутствие истории изменений

**Описание:**
- При обновлении данных старые версии теряются
- Невозможно отследить, когда именно изменились тарифы
- Нет аудита изменений

**Риски при масштабировании:**
- Сложность отладки проблем (невозможно понять, какие данные были в момент оформления)
- Юридические риски (нет доказательств условий на момент продажи)
- Невозможно строить аналитику по динамике изменения тарифов

**Влияние на бизнес:**
- Юридические споры с клиентами и партнерами
- Невозможность анализа эффективности тарифов
- Сложность комплаенс-проверок

**Оценка критичности:** 🟢 Низкая (но важно для долгосрочного развития)

---

### Проблема 7: Неоптимальное использование ресурсов

**Описание:**
- ins-product-aggregator постоянно опрашивается, даже если данные не изменились
- Нагрузка на сервис и базу данных остается высокой независимо от реальных изменений

**Риски при масштабировании:**
- При 10 страховых компаниях и добавлении новых потребителей (например, мобильное приложение):
  - Количество запросов к ins-product-aggregator вырастет в разы
  - Потребуется больше инстансов для обработки
  - Расходы на инфраструктуру значительно увеличатся
- Большая часть запросов будет "впустую" (данные не изменились)

**Влияние на бизнес:**
- Увеличение операционных расходов (инфраструктура)
- Неэффективное использование бюджета
- Необходимость частого масштабирования

**Оценка критичности:** 🟡 Средняя

## Количественная оценка рисков

### Текущее состояние (5 компаний):
- Среднее время ответа ins-product-aggregator: 10-12 секунд
- Вероятность отказа хотя бы одной компании: ~23%
- Количество запросов к страховым в день: 5 компаний × 96 опросов = 480 запросов
- Количество "пустых" запросов (без изменений): ~90% = 432 запроса впустую

### Прогноз при росте до 10 компаний (без изменений архитектуры):
- Среднее время ответа: 20-25 секунд ❌
- Вероятность отказа: ~40% ❌
- Количество запросов в день: 10 × 96 = 960 запросов ❌
- "Пустые" запросы: ~90% = 864 запроса впустую ❌
- **Риск недоступности сервиса: ВЫСОКИЙ**

### Ожидаемые улучшения с Event-Driven архитектурой:
- Среднее время ответа: 1-2 секунды (данные уже в локальном хранилище) ✅
- Изоляция отказов: отказ одной компании не влияет на другие ✅
- Количество запросов к страховым: только при реальных изменениях (~10% = 96 вместо 960) ✅
- Актуальность данных: обновление в реальном времени (0 минут вместо 15) ✅
- **Риск недоступности: НИЗКИЙ**

## Выводы

### Критические проблемы, требующие немедленного решения:
1. ✅ Синхронные вызовы и отсутствие изоляции отказов
2. ✅ Неэффективность polling
3. ✅ Неоптимальное использование ресурсов

### Рекомендуемое решение:
Переход на **Event-Driven Architecture** с использованием:
- **Event Streaming** (Apache Kafka / Yandex Message Queue) для публикации изменений
- **Event Store** для хранения истории изменений
- **Асинхронная обработка** для изоляции отказов
- **Transactional Outbox** для гарантии доставки событий

### Ожидаемые результаты:
- Снижение времени ответа в 10 раз (с 20 сек до 2 сек)
- Снижение количества запросов к внешним API в 10 раз
- Снижение риска каскадных отказов с 40% до <5%
- Улучшение актуальности данных (real-time вместо 15 минут)
- Снижение затрат на инфраструктуру на 30-40%
